● Audited all data paths. Core isolation is solid — no general cross-org leak.

  Properly scoped (no leak)

  Every read/write derives orgId from the session (auth-context.ts) and filters
  on it:
  - orders / review — findFirst({ where: { id, orgId } }) then
  ownership-verified update; cross-org negative tests exist
  (review.service.test.ts:55,83,106).
  - users — updateMany/findMany({ where: { …, orgId } }).
  - mailboxes — deleteMany/findMany({ where: { …, orgId } }).
  - poller — keyed by mailboxId, and a mailbox belongs to exactly one org, so
  replies only match same-org orders (poll.service.ts:68,217).
  - organizations routes — superadmin-only by design
  (organizations.routes.ts:14).
  - logs — only a POST /logs write endpoint exists; no API read path.

  The findFirst(id+orgId) → update(id) pattern is safe because ownership is
  checked first.

  Two real but narrow edges

  1. Mailbox hijack via shared Microsoft account — mailboxes.service.ts:32
  upsert({ where: { microsoftId: graphUser.id }, update: { orgId: input.orgId, …
  } })
  The upsert key is global. If org A has connected a mailbox and someone in org
  B completes OAuth for the same Microsoft account, the update branch reassigns
  orgId to B — moving the mailbox + refresh token across orgs. Requires the
  attacker to actually authenticate that mailbox, so impact is limited, but it's
  a genuine cross-tenant reassignment with no guard.

  2. Email enumeration across orgs — users.service.ts:20
  findUnique({ where: { email: input.email } })  // global
  An admin creating a user learns (via the "already exists" error) whether an
  email exists in any org. Info leak only — no record contents exposed.

  Recommendation

  Neither is a broad leak. If you want them closed: gate the mailbox upsert on
  microsoftId + orgId (or reject when the existing row's orgId differs), and
  make the duplicate-email response identical whether or not the collision is
  in-org. Want me to patch #1?

● Plan written. Direct answer to "how to test the model's confidence":

  Since you chose deterministic rules, confidence becomes a pure function of the
  parsed result — scoreConfidence(result, today) — so you test it the cleanest
  possible way: unit tests, one fixture per rule. No flaky LLM calibration. A
  past-dated delivery, an earliest > latest range, a 6-week-wide window, or
  prose dumped into the order number each deterministically yield low + a
  Romanian reason, and the test asserts the exact routing decision. That test
  file is the confidence's correctness proof.

  The one honest caveat: deterministic tests prove the rules fire as written,
  not that the thresholds (365-day horizon, 30-day max range, 1-day past
  tolerance) match reality. To validate that, the plan's follow-up is to collect
  a handful of real supplier replies with hand-labeled correct fields and
  confirm the rules flag the known-bad ones — then tune the constants. That's
  the step that tells you "low confidence" actually predicts "wrong."

  path as today's missing-field case) → the "verifică" dialog, now with a

  orderNumberConfidence / deliveryConfidence / reviewReasons; a human save

● Yes — that's a genuinely strong technique, and it targets the failure mode the
  sanity rules don't catch: hallucination. It's called extractive grounding /
  provenance checking. The model returns the verbatim span it pulled each value
  from; your code deterministically checks that span actually occurs in the
  source body. If it doesn't, the value was likely fabricated → low confidence.

  Why it fits well here:
  - The verification stays deterministic — the LLM supplies evidence (the
  quote), but the substring check is pure, rule-based code. So it's consistent
  with your "deterministic rules, not self-reported confidence" choice; it's not
  the model grading itself.
  - Cheap — one extra field per value in the same call, no second request,
  provider-portable.
  - Best for orderNumber — an order number is a literal token that should appear
  verbatim. A fabricated one fails the check immediately.

  The important caveats:
  1. Match the quote, not the parsed value. Delivery dates are normalized to ISO
  (2026-06-20) but the email says "20 iunie" / "20.06". So you verify the
  model's quote ("20 iunie") is in the body — the resolved date is then covered
  by the existing past/range sanity rules. Don't substring-match the ISO.
  2. Normalize both sides before matching (collapse whitespace, lowercase,
  optionally strip diacritics) or you'll get false "not found" from
  reformatting.
  3. Text input only. For PDF/image there's no source text in code to match
  against (the model read pixels), so grounding-by-substring doesn't apply there
  without OCR.
  4. It catches fabrication, not misattribution (a real token used for the wrong
  field). So it complements — doesn't replace — the sanity rules.

  One real tradeoff vs. the current plan: it adds a quote field to the
  extraction JSON schema + a prompt line, which means touching the extraction
  call (extraction.ts) that the current plan deliberately left untouched. Worth
  it for hallucination detection, but it's added scope.
