     FlowForge — Feature-Based SaaS Foundation

     Context

     Trenda is a working Fastify + React multi-tenant email-automation app
     (orders →
     poll inbox → LLM extract → reply to vendors via Microsoft Graph;
     appointments →
     collect customer info). We are evolving it into FlowForge, a feature-based
     SaaS platform where superadmins assign sellable features to companies,
     and customers only see UI for the features assigned to them.

     This first deliverable builds the foundation only:

     - a feature registry (product catalog, code-defined),
     - per-company feature assignment + config (DB),
     - access control + UI gating so customers only see assigned features,
     - a superadmin assignment UI,
     - an execution router (executeFeature + n8n/node adapters) as scaffolding
     for future features.

     Explicitly out of scope (per user): sendMessage, any new feature
     (WhatsApp/SMS/etc.), real provider integrations. The two existing pipelines
     are
     wrapped, not rewired — registered as features vendor_communication and
     customer_communication for access-control/UI-gating, while their current
     Microsoft-Graph execution stays byte-for-byte the same.

     What already exists (reuse, don't rebuild)

     - Tenancy: Organization model = the "company". User.role ∈
     member|admin|superadmin. Guard requireRole() in
     backend/src/lib/auth-context.ts.
     - Superadmin layer:
     backend/src/modules/organizations/organizations.routes.ts
     (superadmin-gated via preHandler). Frontend frontend/src/pages/admin.tsx.
     - Identity to frontend: GET /auth/me → mePayload(user) in
     backend/src/system/auth/auth.routes.ts; consumed by frontend/src/lib/auth.
     - Existing "email automation": orders pipeline (modules/orders,
     modules/poll,
     lib/microsoft.ts:createAndSendMail/replyToMessage) + appointments
     (modules/appointments). These remain technical modules, untouched at
     runtime.

     Design decisions

     - Feature definitions live in code (typed registry), not a DB table — Node
     is
     the long-term source of truth. OrganizationFeature (DB) holds only
     per-company
     state (enabled + config). featureKey is a validated string, no FK.
     - executionType: "native" | "n8n" | "node".
       - native = handled directly inside an existing module (current behavior);
     the
     execution router is not involved. Both seed features are native.
       - n8n / node = future features routed through executeFeature.
     - Modules stay technical; business features live in the new features/ +
     execution/ layers. No business logic moves into modules.

     Proposed folder structure (additive)

     backend/src/
       features/                 # NEW — product layer (definitions only, no
     execution)
         registry.ts             # typed FeatureDefinition map +
     getFeature/listFeatures
         definitions/
           vendor-communication.ts
           customer-communication.ts
         types.ts                # FeatureDefinition, ExecutionType, config

       execution/                # NEW — hidden runtime (scaffolding)
         execute-feature.ts      # executeFeature(orgId, featureKey, payload)
         router.ts               # resolves executionType -> adapter
         adapters/
           n8n.ts                # webhook POST (MVP)

         types.ts
       system/

     Implementation steps

● Good question — it's the most important modeling decision in the whole system,
  because the feature key is your SKU: it's simultaneously the billing unit,
  the access-control unit, and the UI-gating unit. Granularity of the key =
  granularity of all three.

  Three ways to cut it:

  A. Capability is the feature; channel/variant is config (recommended)
  - Feature = the outcome a customer buys: appointment_reminders,
  review_requests, lead_qualification.
  - config holds channel: "whatsapp" | "sms" | "email", timing, templates,
  thresholds.
  - The n8n workflow / node handler reads config and routes internally (exactly
  your "route between config values inside the workflow").

  B. Channel is the feature (whatsapp), behavior is config
  C. Fully granular (whatsapp_reminder, whatsapp_review, …) — each its own
  feature

  Why A wins on business grounds:

  1. Customers buy outcomes, not channels. Nobody buys "WhatsApp" — they buy
  "reminders that reduce no-shows." Channel is delivery, an implementation
  detail. Naming the feature whatsapp_reminder (C) welds the product to the
  pipe, so the day you offer the same reminder over SMS you either rename the
  SKU or duplicate it.
  2. Catalog explosion. C gives you channel × capability (whatsapp_reminder,
  email_reminder, sms_reminder, whatsapp_review…). A keeps it linear — one
  feature per capability, channel is a knob.
  3. Access/billing granularity. B (whatsapp) is too coarse: you can't sell or
  show "reminders" without also exposing "review requests" — they're the same
  feature. The whole point of the system is gating sub-capabilities
  independently. A gives you exactly that granularity without the explosion of
  C.
  4. Bundling stays composable. Keep features atomic (capability-level) and
  later compose them into plans (Starter/Pro). You can always bundle narrow
  features; you can't cleanly unbundle a broad one.

  The heuristic line: Is it billed or shown/hidden independently? → it's a 
  feature. Is it a knob on the same capability? → it's config. So channel,
  schedule, copy, thresholds = config. A genuinely separately-sold capability =
  new feature.

  This fits what's already there: vendor_communication / customer_communication
  are capability-named and channel-agnostic — consistent with A.

  If you take A, I'll fold it into the plan: feature definitions get a real
  configSchema (channel enum + variant knobs), and the execution adapters route
  on config rather than on the feature key.

  How the JSON configs work

  Two layers:

  1. Storage (per company): every OrganizationFeature row has a config JSON
  column — the settings for that feature, for that company. It's keyed (orgId, 
  featureKey), so VerifyCo's vendor_communication config is independent of any

  configSchema (a Zod schema). It's the contract for what's allowed in that
  JSON.

  Right now both seed features have no configSchema, so config is free-form —
  the superadmin UI shows a raw JSON textarea, and setOrgFeature accepts any
  object. That's why you saw hasConfigSchema:false in the verification.

  Where config is consumed: executeFeature loads the company's config and hands
  it to the adapter — the n8n adapter reads config.webhookUrl; node handlers get
  ctx.config. So config is how one capability is tuned per-company (channel,
  templates, thresholds, webhook URL…). This is the "channel-as-config" model
  from the plan.

  Can you extend them easily? Yes — two levels

  Free-form (today, zero code): type any JSON in the superadmin textarea. Stored
